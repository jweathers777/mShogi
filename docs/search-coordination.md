# Search request coordination

MSH-21 adds `mshogi_search::coordination::SearchCoordinator`, a native worker around the existing stop-aware full-width search. It owns one worker thread, one replaceable pending request and one completion slot. It emits no progress stream and performs no console/protocol I/O. Search never runs while holding the coordinator's metadata mutex, and it works on private game snapshots.

`submit(&game, version, limits)` returns an immutable `RequestContext` with a process-unique opaque `RequestId`, the consumer's revision number, the exact canonical `GameRecord` and deterministic search limits. The record includes initial position, imported-history provenance, claim policy, complete known move history and any exercised claim. Neither board identity nor ply count replaces that context. Versions may repeat: IDs are never reused, including across coordinators; identity exhaustion is an explicit submission error rather than wraparound. Invalid limits leave existing work untouched.

Submitting cancels earlier work, replaces the pending slot and clears the stored completion. The worker discards a result if its identity is no longer current. `poll()` consumes the one current completion envelope, including explicit `SearchError` failures. Envelopes held by a consumer may still become stale after polling. Immediately before acting, call `accept_result(&completion, &current_game, current_version)`. It verifies current request identity and context, supplied version and exact current game record. A board that returns to an earlier appearance, a reused version, imported history replacing known repetitions, or a position change without a revision bump cannot make an old request acceptable. Rejection leaves the game unchanged.

The consumer must serialize submissions, game changes and acceptance/application in its game event loop; acceptance does not lock the consumer's game or apply an action. Do not validate in one thread and later apply in another without rechecking context. Accepting a search envelope also does not turn an incomplete iteration or `SearchError` into a usable chess decision. Handle those explicit values according to the adapter's documented fallback/failure policy.

`cancel()` sets the current request's atomic stop flag and returns its ID without waiting for search or joining a thread. It deliberately preserves current identity so a UCI `stop` can receive the last completed iteration. Even a cancelled request that was still pending runs only far enough to produce a stopped, zero-node completion. `acknowledged(&context)` becomes true once that request is neither pending nor executing. Superseded pending requests are acknowledged without executing; superseded active requests are acknowledged once the worker unwinds. If search had already completed, cancellation is already acknowledged and the existing complete result remains valid.

Cancellation acknowledgement is bounded in search work by the current node's rules processing and private branch unwind: the search polls the atomic flag before each next node visit. This is a cooperative work bound, not a hard real-time wall-clock guarantee. Metadata critical sections contain only small state/Arc/atomic operations; expensive snapshot construction, exact history comparisons and retired snapshot destruction occur outside those sections. Cancellation may briefly contend on that mutex and both caller/worker depend on OS scheduling. There is no wait on a full progress queue, blocking channel send, or worker join. Tests use generous wall-clock deadlines solely to catch hangs; their deadlines are not product latency promises.

`shutdown()` cancels active work, removes pending/results and rejects new submissions. `shutdown_acknowledged()` observes worker exit. `Drop` requests shutdown and detaches without joining; a worker still inside a node exits cooperatively. Reuse a coordinator for an engine session instead of repeatedly constructing and dropping workers. There is one worker per live coordinator, with at most one transient finishing worker after its owner drops. Fixed slot counts bound queue growth, not the size of input game histories or completion envelopes retained by a consumer. Each snapshot's memory scales with the supplied known game record.

A timed adapter can track its own monotonic deadline, poll completions and call `cancel()` on expiry. Deterministic node/depth limits remain part of the request context. Timed observations must additionally be recorded by that adapter; identical timed reruns are not promised. Machine stdout formatting, UCI scheduling and process-failure reporting remain adapter/runner responsibilities.

Focused verification: `cargo test -p mshogi-search --locked` exercises real native worker completion, caller preservation, cancellation while demonstrably active and before completion, delayed results after game changes, exact same-position/different-history rejection, ABA versions, identities across coordinators, 200 rapid replacements, invalid submission preservation and shutdown acknowledgement. Existing search oracle, policy, work-limit and evaluator tests remain applicable. `cargo clippy -p mshogi-search --all-targets --locked -- -D warnings` checks the changed crate and targets; platform evidence and independent review are recorded in MSH-21.
