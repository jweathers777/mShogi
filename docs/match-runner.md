# Chess match experiments

MSH-23 connects UCI subprocesses to the rules-owned `ChessMatch`. Engines propose coordinate actions; only the rules library accepts them, updates history and clocks, exercises valid claims, and concludes chess outcomes. The runner provides experiment supervision and records. It does not infer a result from an evaluation or an engine's draw/resignation suggestion.

```sh
cargo build --release --workspace --locked
target/release/mshogi-match run CONFIG.json REPORT.json
target/release/mshogi-match replay REPORT.json
```

On Windows the executable names end in `.exe`. Run configurations resolve executable/model paths from the working directory; use explicit paths. Arguments are passed directly, without a shell or PATH lookup. Report creation refuses to overwrite an existing file. A completed experiment report can contain unscored failures; inspect its per-game status and summaries rather than treating report creation as proof that every engine succeeded. Replay validates the report without starting its engines.

The committed [experiment configurations](../tests/fixtures/matches/) are concrete schema-1 examples. They identify two engines with path, argument array, ordered UCI options, optional model file, declared embedded model/evaluator identity and a deterministic-settings declaration. Openings have distinct IDs, optional imported FEN and complete prefix actions. The configuration also records pairing, claim policy, clock control, depth/node/movetime work limits, maximum plies, watchdogs and I/O bounds. Effective defaults are serialized into the report. External model files and executables are SHA-256 fingerprinted separately; an embedded model is covered by its executable fingerprint, with the declared model label retained.

Each game starts fresh engine processes and completes UCI handshake, options and readiness before starting its chess clock. Both colors and their executable identities are recorded. Openings can be paired with reversed engine assignments. A match from an imported FEN knows only the history beginning there, including explicitly supplied subsequent actions. It preserves the supplied counters and cannot reconstruct earlier repetition occurrences.

The initial runner accepts recorded `auto_claim` policy: at a turn boundary, actual conclusions take precedence, then the controller exercises the rules-selected valid current or intended-move claim before requesting another engine move. Intended actions remain unplayed. Other policies remain available in the core and UCI adapter; this unattended runner has no explicit claim channel. For mShogi engines the controller selects the advertised `ClaimPolicy auto` option so future search nodes follow that same policy. UCI has no standard claim command; external engines still supply moves while the controller owns claims and match adjudication. An external engine's internal search policy is its own implementation and must not be mistaken for a second rules authority.

Untimed experiments and single-stage Fischer increment clocks use the [match profile](rules/chess-match-v1.md) and its [event ordering](rules/chess-match-api.md). The runner observes monotonic timestamps and records the arrival of complete responses. Core arrival/flag precedence and increments are recomputed from those observations during replay. Process watchdogs are separate from chess clocks. A required reply that has not arrived by a watchdog deadline is an experiment failure; an observed chess-clock expiry is submitted to the core. Under default M2 recognition, a timeout requiring unproved mating possibility remains explicitly unresolved and unscored.

Arrival means the controller's receipt of a complete line. That captured timestamp survives parsing, logging and diagnostic exit-status collection; an on-time move cannot become late solely because bookkeeping took time. UCI clock values project the active balance to the recorded `go` dispatch time, while the core retains the fixed actual deadline and charges transport time. If the controller wakes after both watchdog and chess deadlines, the earlier established deadline wins; chess wins exact ties. Failure `at_ns` preserves the actual observation and separate `deadline_ns` identifies an expired watchdog. A delayed wake is not presented as an observation made exactly at the deadline. EOF before a later flag remains a process failure even if a brief status check finishes after that flag.

## Reproduction promises

Canonical game and match records replay deterministically from their initial state, policy, commands and observed clock events. Replay does not launch an engine or estimate time by repeating a search. A corrupted move, clock reply, result or configuration must fail validation rather than be silently repaired.

The report retains an effective-configuration checksum, checks executable/model declarations against that configuration, and validates retained setup, position and work commands against replayed match contexts. Checksums detect inconsistent edits; reports are historical observations, not signed proof of authenticity. Truncation of protocol/diagnostic evidence is explicit. The canonical core match records remain complete even if bounded ancillary transport evidence is truncated.

Rerunning engines is a different operation. A deterministic move-history claim requires the same executable/model identities, options, initial known history, deterministic engine settings and deterministic work limits. The mShogi baseline uses stable action ordering, single native search and depth/node limits. An independent engine needs its own documented deterministic settings; a fixed node budget alone does not establish this for an arbitrary engine. Fresh processes avoid inheriting transposition state from earlier games. Recorded wall-clock measurements and process scheduling observations need not be byte-identical even when moves repeat.

Timed runs preserve settings, commands, observations and outcomes. They make no identical-rerun promise. Changes in machine load, scheduling and communication can change completed search work and flag timing. Replay of their *recorded* observations still has one deterministic meaning.

Process start failure, unexpected exit, invalid action, missing required response and response timeout are recorded failures with diagnostic evidence and no invented chess score. Experiment limits likewise do not become agreed draws or evaluation adjudication. An actual prior rules conclusion remains final; later cleanup trouble is diagnostic evidence rather than a replacement chess result.

The bounded runner drains engine output, limits retained diagnostics/transcripts, and supervises writes and cleanup as well as responses. Defaults are 5-second handshake/readiness, 10-second move-response, 2-second write and 1-second cleanup watchdogs; 4096-byte stdout lines/commands, 32 queued stdout events per child, 256 KiB retained transcript per game and 16 KiB retained stderr per child. Identity metadata has separate 32-line/4096-byte caps and an `identity_truncated` marker. Transcript accounting includes entry overhead, preventing empty-line floods from growing metadata without consuming the cap. Nonregular executable/model artifacts are refused before opening them; fingerprint input is bounded to 2 GiB.

Configurable bounds are validated, with at most 32 openings/64 games when paired and 512 total plies per game including its prefix. A conservative aggregate configuration bound leaves room beneath the 128 MiB report decoder limit. Reaching a bound must remain visible. These supervise local processes and depend on OS scheduling; they are not hard real-time guarantees. The fixture binary is process-test support, not an independent chess opponent.

## Evidence

The [recorded experiment corpus](../tests/fixtures/matches/README.md) supplies exact configuration, executable fingerprints, commands and outcomes: thirteen first-run games and eight additional work-limited rerun games. It includes complete self-play and Stockfish 19 games from both a forced ending and the standard start, timed increment play, known-history claims and a genuine unscored search failure. A real outstanding UCI search also terminates through clock expiry and quit, retaining actual delayed detection and an explicitly unresolved score. The repeated untimed games have identical command histories and conclusions under the documented settings. Timed observations are preserved without that promise.

`cargo test -p mshogi-runner --locked` covers four deterministic timing seams, eight portable child-process/configuration tests, two Unix-only boundary tests, and four actual-evidence replay/comparison tests. Independent process and rules/report reviewers resolved configuration binding, timestamp preservation, deadline precedence and output-bound issues. MSH-23 records exact source/native CI; MSH-25 verifies focused milestone integration. The independent engine was actually run on macOS; native Linux/Windows tests run the portable fixture and replay its recorded evidence.

No strength conclusion follows from a few games, a forced ending, or interoperability. Competitive evaluation needs separately scoped opponent pools, opening distributions, paired samples and statistical evidence in M5. The desktop and other five target games remain future work.
