# Executing later 20M adjudication with the frozen cloud worker

Bounded source review, execution_review, 2026-11-12. No jobs, engines, configuration changes, rebuilds or waiting for current computation. Inspected `core.py`, `cli.py`, `chess.py`, and the actual recovery probe submission/spec.

## Existing mechanism is sufficient

Use a **separate immutable adjudication plan and explicit `core.run_job` calls in the existing pinned image**. The cloud recovery probe already demonstrated this execution route: its Batch runnable overrides the container entrypoint to `python3 -c`, verifies an existing result, seals a distinct confirmation job, calls `run_job`, and proves immutable-success reuse. This establishes that explicit jobs can run without publishing another pipeline manifest or replaying games. The 20M scientific plan itself still needs review; the recovery demonstration was a 5M infrastructure check, not 20M evidence.

`chess.execute` accepts confirmation nodes from 1 through 20,000,000. A confirmation with an explicit `move` performs one forced query; a confirmation with `move=None` performs unrestricted and played queries at the same node limit. Both use the original native report, native replay, exact selected game/ply and full history; each query retains the frozen 60-second/process-cleanup bounds. No worker rebuild is required for these capabilities.

Do not use the ordinary `prepare`/`submit` path to overwrite `experiment/manifest.json`, or alter the saved screen-derived 5M plan. `publish_manifest` is create-only and rejects different content. `validate_manifest` requires game-pair roots and complete dependency membership; a confirmation-only manifest is rejected. An expanded same-experiment manifest could satisfy structural validation if parents were included, but cannot replace the original published manifest and is not the recommended route. Moving jobs to a new experiment without moving parents also fails the same-experiment dependency check.

## Concrete plan and execution contract

1. After completed-batch review, create a versioned plan at a new key such as `EXPERIMENT/adjudication/PLAN_ID/plan.json`. Bind the original manifest hash, reviewed scientific selection/reasons, consumed screen/5M result hashes, source report identities, exact game/ply, actual played move and every requested alternative. Include all required consequential decisions and audit-expansion obligations; preserve unresolved alternatives. Preflight legal histories and moves before publication. Publish create-only, accepting an existing key only if its bytes are identical.
2. Derive each job from the same frozen source/build/environment fields as its verified screen or confirmation. Keep its `experiment` and original game-pair `inputs.report` dependency; set `kind='confirmation'`, `nodes=20000000`, exact game/ply and explicit forced `move`. Retain required analysis/screen outputs. Attach the scientific selection/provenance and a stable plan identifier, then `core.seal` and validate. Do not mutate a 5M job under its old ID. Deduplicate identical canonical root/move/budget requests within the plan.
3. Avoid circular hashes: seal jobs using a stable plan ID and separately hashed selection payload; then hash the final plan containing those jobs. Bind that final plan hash in the submitted task specification and dispatcher, rather than embedding it into the very jobs whose IDs it helps determine.
4. Use a small, reviewable submitted dispatcher, following the recovery probe's pinned-image `python3 -c` route. Fetch and verify the plan's exact SHA256; select an explicit bounded task assignment using `BATCH_TASK_INDEX`; verify every planned job and relevant parent success; call `core.run_job(job, store, cli.REPO)` sequentially. The frozen API retains source/binary/environment checks, dependency artifact verification, immutable results, claims, failure receipts and cleanup. It must only receive confirmation jobs and never invoke `pipeline()` or a game-pair job. Record the dispatcher bytes/hash and full Batch request with the plan. Do not add a new dispatcher hash to frozen `source_files` as though it existed inside the old image.
5. Keep the same pinned worker image and C3 allocation, at most the established eight simultaneous workers, with explicit task/run/retry bounds and existing Pub/Sub exit notification. A bounded assignment can contain several sequential queries to avoid provisioning a VM for every short query. Submission is an orchestration-only Batch runnable override; do not weaken the original image checks or modify its installed sources.
6. At completion verify every plan job with `core.verify_result`, including artifact hashes and matched equal-work pairs, and publish a separate immutable completion receipt binding the plan and all results. Retain attempts and uncertainty; completion is not scientific confirmation. A missing result or unsettled claim makes the plan incomplete.

For discovery cases use `move=None` to obtain unrestricted plus played 20M reports, inspect the returned root move in completed evidence, then freeze a small second plan forcing any distinct discovered alternative at 20M. An unrestricted score does not substitute for the required equal-work singleton alternative. Same-choice controls can be deduplicated while preserving their interpretation. No automatic model supervision of individual searches is needed.

## Accounting, notification and recovery gaps to handle explicitly

The ordinary `cli.all_jobs` enumerates only the published static jobs plus deterministic screen-derived 5M jobs. Consequently ordinary `verify`, `status`, quick status and recovery selection do **not** establish completion or expose every extra 20M obligation. Do not report a successful standard manifest status as a completed adjudication plan.

`retrieve` copies the whole experiment prefix, so it can carry the extra plan and receipts, although its returned status remains limited to the standard graph. `report` sums attempt receipts under the experiment's jobs prefix, including explicit 20M jobs; it is an aggregate and must be separated by node budget/plan to avoid double-counting prior work or conflating attempts with decisions. Preserve failed attempts and VM lifecycle overhead. A plan-aware local verifier/report is the smallest useful controller-only addition if reusable orchestration is desired; it need not change core, the frozen adapter or image.

The reviewed `wait-cloud` listener can observe the new Batch job by name/config and store its terminal event without requiring its container command to be the normal pipeline command. The quick-status `--job-name` binding check, however, expects `cloud-worker --manifest` and will reject a custom dispatcher. Use the recorded adjudication submission plus plan-aware status, not a weakened main-manifest binding check.

On an interrupted explicit job, keep the original claim and attempt evidence. The ordinary `recover --job` cannot find jobs absent from `all_jobs`. Use a narrowly reviewed plan-aware recovery operation: load and validate the exact plan/job, establish that its owning worker has stopped, write an immutable recovery record, and generation-conditionally remove only that claim. This mirrors existing core/store behavior; never clear claims merely because a retry is desired. Re-running the same explicit job verifies and reuses immutable success rather than recomputing it.

## Recommendation

Use the demonstrated explicit-job route with a reviewed, hash-bound plan/dispatcher and plan-aware verification/accounting. No competing runner, production change or worker rebuild is needed. The limited new work is orchestration and evidence enumeration for an existing adapter capability. Keep all 20M, audit-expansion and final adjudication obligations open until their explicit plans and independent reviews are complete; current 500k/5M pipeline success cannot close them.
