# Standard shogi independent verification proposal

Planning record for MSH-62, researched 2026-10-26. This is a proposed verification contract for MSH-41 and its children, not implementation, an executable fixture suite, or evidence that mShogi shogi works. Current selection update (MSH-63): John approved SHOGI-P1 option A in [the selected profile](shogi-profile.md); `mshogi.shogi.csa36.v1` uses JSA movement with explicit CSA-36 event conclusions. The JSA professional replay convention is a separate alternative. The [fixture inventory](shogi-fixtures.md) records independent expectations and unresolved cases.

## Distinct evidence roles

| Role | Proposed source | What it establishes |
| --- | --- | --- |
| Governing rule authority | Versioned JSA-R, JSA-E and applicable supplemental JSA pages; CSA-36 only for an explicitly selected computer-event profile, as catalogued in the profile proposal | The approved rule and match policy; resolve inconsistencies before fixtures acquire final outcomes. |
| Independently expected fixtures | Hand-derived small positions and full event histories, tied to a rule clause and reviewed separately from the implementation and reference | Expected choices, state changes and results. A reference's output never supplies the sole expected answer. |
| Differential implementation | The pinned cshogi source below, operated only through the audited subset | Agreement/disagreement on complete board moves and state transitions within shared semantics. Agreement is useful corroboration, not proof. |
| Integration opponent | Pinned YaneuraOu material engine candidate below, with explicit option/profile compatibility | Real USI interaction, legal play, complete history transport, cancellation and result handling; no strength claim. |

The historical C++ mShogi engine is a regression-idea source, not a rule authority or independent conformance oracle. cshogi's source credits Apery/Stockfish, and contains adaptations from YaneuraOu; the two proposed external programs are separate executions with shared lineage, not two fully independent rules implementations. The rule-clause derivations and fresh independent review remain necessary. The actual reviewer method must be recorded; MSH-64 uses a separate AI-agent review and does not claim a human review.

## Differential procedure and acceptance evidence

Future delivery should first admit the pinned reference using the independent sentinel fixtures, then compare complete move sets at each prefix of reviewed histories and deterministic valid playouts. Record root, profile/version, history scope, seed and each move; on disagreement retain the smallest replayable prefix and both outputs. Decide the expected answer from the rule and independently reviewed geometry/history. Never regenerate expected results from whichever implementation is under repair.

For each legal move compare placement, promotion, capture demotion into the correct hand, side, exact hand counts and counter progression; unwind to each prior snapshot. Add color/board-rotation equivalence, capture/drop material conservation and replay/undo equivalence as secondary checks. Those properties help find defects but do not replace expected cases. Perft counts become durable expected counts only after independent enumeration/review; this proposal deliberately invents no shogi node totals.

History/match comparisons use a separate profile-aware expected event ledger, including board actions, declaration/resignation/confirmation, timeout and administrative outcomes. It must retain evidence of whose check continued, whether an outcome is pending, a replay relation and score. An identical position reached with different occurrence history need not have the same available match actions. Search admission must test that terminal and policy actions survive complete-action transport, and that bounded/cancelled search restores the root and cannot apply stale results. Passing conformance establishes rules behavior; it does not establish engine strength.
