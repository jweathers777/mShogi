# Chess match and history profile v1

Profile ID: `mshogi.chess.match.v1`. Position/move semantics remain [`mshogi.chess.position.v1`](chess-position-v1.md). This is an MSH-15 specification for MSH-16–18, MSH-20–23 and MSH-25, with implemented coverage recorded in the ledger. MSH-16 supplies the [history/record foundation](chess-history-record-v1.md), MSH-17 the [live adjudication boundary](chess-adjudication.md), and MSH-18 the [match commands/clocks and semantic replay](chess-match-api.md). Full dead-position/possible-mate completeness remains MSH-26. Owner authority: John's 2026-10-24 batch instructions, recorded in MSH-15. Internal APIs, concrete chess record encoding and representations belong to the implementer; neither a universal six-game schema nor a transposition-table design is a prerequisite.

Primary reference: [FIDE Laws effective 2023-01-01](https://handbook.fide.com/chapter/E012023), English version, consulted 2026-10-24. Pin this edition rather than silently tracking later revisions. Article references below refer to it. Physical touch-move, clock pressing, scoresheets, arbiter penalties, illegal-move forfeits and tournament administration are outside this software profile. M2 is an honest bounded implementation, not tournament certification. Software interpretations below are project policy, not extra FIDE rules.

## State and identity

The rules-owned game contains the current validated position, known initial position, ordered complete actions, rule-relevant history, concluded status and command state. Match state adds player assignments, offer state, policy and clocks. Every accepted action/command is atomic; rejected requests preserve game state. Undo/analysis branching restores all rule-relevant state, not just the board. A concluded game cannot accept further play/claims; analysis undo is an explicit branch operation, not a retroactive live-match command.

Saved position equality includes all six FEN fields. Repetition equivalence (9.2.3) uses board pieces, side to move, castling rights and **legally available** en passant. Omit a raw EP target if no legal EP capture exists, including a pinned pawn's illegal EP. Keep castling rights even if a path is blocked or attacked. Ignore counters for repetition. Maintain exact identity or collision verification; a hash alone cannot establish a draw. This defines no future cache scheme. Search must preserve history-sensitive semantics and cannot reuse adjudication by board identity alone.

Importing FEN creates occurrence one of the initial position and a `prior_history_unknown` origin marker. Never infer earlier repetitions from counters, opening knowledge or the diagram. Preserve the supplied halfmove/fullmove counters, including zero halfmoves and large fullmove numbers. They remain authoritative for the 50/75-move tests under this import contract, although they are not proof of historical reachability. Standard start has a known start-of-game origin. Offer eligibility counts actions observed in this record, not inferred fullmove numbers. Record/reset the origin on replacement; undo cannot invent earlier history.

## Outcomes and optional claims

Keep `ongoing` (possibly with claim opportunities), exact concluded chess outcomes, unresolved/unscored termination, and engine/experiment failure distinct. An available claim is never itself a concluded outcome. The core exposes optional claim commands for the side to move:

- Threefold: current occurrence count at least three, or an explicitly supplied legal intended action would produce at least occurrence three (9.2.1–2).
- Fifty moves: current halfmove count at least 100, or a legal intended action would make it at least 100 without a pawn move or capture (9.3). A resetting action cannot qualify.

Validate an intended action on private state, without committing it. A valid claim concludes a draw **before** the intended action is played; record the proposed action and evidence, not a fictional played move. Reject invalid claims atomically, with a reason; no clock penalty or forced intended move is imposed in this software API. This deliberately omits the physical/arbiter procedure of 9.4–5. Claims are not available after a terminal result, even if the counters would qualify.

After initial import and after each committed legal action, classify in this stable diagnostic order: checkmate (5.1.1), stalemate (5.2.1), recognized dead position (5.2.2), fivefold (9.6.1), then halfmove count at least 150 (9.6.2). All are automatic. Checkmate on the last actual move therefore overrides the 75-move threshold. If multiple draw reasons hold, the first supplies the primary reason and other established reasons may be recorded; never change the score. Prior concluded results outrank later commands and observations. An intended claim made before a prospective mating move can end the game first; projecting a move to validate a claim does not commit its automatic outcomes.

The initial unattended runner uses recorded `auto_claim` policy: before requesting a move, exercise a valid current claim, otherwise any valid intended claim (threefold before fifty, coordinate actions sorted a1..h8 with promotion q/r/b/n). The core also supports `explicit_only`, under which opportunities remain player choices. Search consumes the rules-owned game and selected policy: auto-claim nodes are draws when the policy will claim; under explicit-only, a claim is an optional zero-valued choice, not a forced draw or proof that every continuation draws. Search checks actual outcomes before static leaves. UCI cannot express these commands: the controller owns claims and logs them; no invented UCI token is required.

## Sound bounded recognition and mating feasibility

M2 recognizes dead positions only when, besides both kings, there are: no pieces; exactly one bishop or knight total; or bishops only and **every bishop occupies the same square color** (either color of player, any count). No pawns, rooks, queens or knights may be present in the bishops-only case. These are sufficient proofs: lone minor cannot mate a bare king; same-color bishops cannot cover the opposite-color escape geometry. Two knights are deliberately not recognized, and opposite-color bishops are not automatically dead. Blocked pawn structures and many other dead positions are outside this recognizer.

The result is `proven_dead` or `unknown`, never `not_dead` on a failed recognition. Full detection and side-specific possible mate remain **MSH-26, M4 chess completeness**. The ledger must retain that obligation after M2 closes.

For resignation (5.1.2) and flag fall (6.9), establish whether the **opponent** can mate by any legal sequence, not whether it can force mate. A bare king cannot mate; a recognized globally dead position also proves neither side can mate. Other side-specific impossibility needs an explicit sound proof. Positive evidence is a verified finite legal continuation ending in that side delivering checkmate; it may be found with a bounded witness search or supplied as a checked certificate. Record the witness/proof and work bound. Never infer possibility from material advantage, a static score, or failure of the dead recognizer. When neither possibility nor impossibility is established, terminate with `unresolved_mating_feasibility`, actor and trigger, and **no chess score**. The M2 implementation may consequently leave many time/resignation terminations unscored. This is an approved limitation, not a draw. Already concluded automatic results take priority.

## Match commands and clock ordering

Commands carry actor and game version. Resign uses the feasibility rule above. Offer/accept/decline draw are separate from board actions (5.2.3, 9.1); agreement is allowed only after each player has made at least one recorded move. Only the opponent accepts a pending offer. Offers persist until acceptance, explicit rejection, the opponent's next committed move, or conclusion; the offering player's move alone does not withdraw it. A repeated offer cannot withdraw a pending one. An invalid claim is also an offer under 9.1.2.3 only if explicitly requested as a separate valid offer command; the failed claim itself is atomic. Record this software simplification of tournament procedure. Evaluation-based resignation and draw adjudication are disabled initially.

Support untimed experiments and one basic Fischer-increment clock: positive initial balance for each side, nonnegative increment, integer monotonic elapsed units (record the unit, use nanoseconds in the native runner). No delay, staged controls, lag compensation or tournament procedures. Reject decreasing timestamps and arithmetic overflow explicitly; do not silently saturate a result. Clock tests inject time; they never sleep. Initialization is outside a player's clock: start the active side immediately before its first move request. Subsequent request/transport time is charged to the active side. Handshake/readiness have separate recorded watchdogs.

One controller serializes versioned events with monotonic timestamps plus sequence numbers. At a move/command arrival: (1) retain any prior conclusion; (2) charge elapsed active time through arrival; (3) if balance is zero or less, record flag fall and adjudicate feasibility before accepting the move/command; (4) otherwise validate and commit, then apply immediate game conclusions/claims; (5) for an accepted nonterminal move add the increment exactly once and start the opponent at the same timestamp. A terminal move stops clocks and receives no increment. A rejected command gets no increment and the same side keeps running; elapsed time is still charged. An explicit valid claim stops clocks at its arrival. An unattended auto-claim is serialized at the turn boundary before requesting another move. Simultaneous boundary events use sequence order; arrival **at** the deadline flags, while mate committed strictly before it wins. The move is atomic software completion, so there is no separate physical clock press.

Chess-clock expiry and protocol/watchdog expiry are different. If a clock deadline and process failure are both observed, serialize the earliest established event; for the same timestamp use clock expiry first, then the observed process event as diagnostic. A previously concluded game cannot be replaced by a failure. Untimed mode has no chess flag fall, but finite configured protocol watchdogs still apply.

## Records, UCI and failure reporting

A chess record carries schema/profile versions, initial state, history-origin marker, ordered complete actions and game commands; match records additionally carry policy, offers/claims and intended actions, proof/witness details, timestamped ordered clock events/balances, engine identity (path/version/hash, arguments and model identity if any), settings, work/time/watchdog limits, openings/colors and result or failure evidence. Store UCI commands/responses and bounded diagnostics with truncation markers. Events reference the game version. Replay validates actions, commands, timestamps, balances and result from recorded observations and rejects inconsistencies. It never infers elapsed time by rerunning an engine. Concrete encoding is an implementation choice for its real consumers; public records exclude private undo layout and client-authored effects.

UCI is the first adapter ([original April 2006 specification by Stefan Meyer-Kahlen](https://www.shredderchess.com/download/div/uci.zip)). MSH-22 documents supported handshake/readiness, position plus moves, work/clock commands, stop and quit. MSH-23 depends on that adapter and records an actual match against an independent UCI engine, with identity and commands; a toy subprocess alone is insufficient interoperability evidence.

The runner reports `process_start_failure`, `unexpected_exit` (including signal/exit code), `invalid_move` (raw bestmove and rules rejection), `missing_response` (EOF or no required reply), and `response_timeout` (phase, configured watchdog, last observed output). Illegal output never mutates the game. A live silent process becomes response_timeout at the watchdog; EOF before the required reply is missing_response, with exit information when available. Cancel/kill/reap failed children with bounded cleanup and record cleanup failures. These are unscored experiment failures, not chess forfeits. Optional separate failure statistics do not invent a chess result. Preserve already established outcomes and record subsequent process problems diagnostically.

Replay of recorded games/events is deterministic. A fresh engine rerun is deterministic **only** with documented deterministic settings and work limits (for example one thread, fixed node/depth budget, fixed seed, no timing-dependent options). Timed experiments retain configuration and observations but do not promise identical move sequences or elapsed times. No strength claim follows from a small interoperability match.

## Fixtures and delivery

[match-profile.json](../../tests/fixtures/chess/match-profile.json) is a declarative, hand-derived specification family. The preparation test checks IDs, positions and legal action paths against existing M1 boundaries; it does **not** execute future adjudication. Each later owner must consume the expected semantics in behavioral tests, including the same current position with different histories, claim versus result, mating uncertainty and exact clock boundaries.
